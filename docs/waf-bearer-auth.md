# KrakenWAF observability authentication

Kraken UI 0.12.0 authenticates requests to KrakenWAF's dedicated observability
listener with an HTTP bearer token. The listener uses TLS and defaults to port
`4343`; Kraken UI therefore normally connects to:

```yaml
waf-endpoint: "https://127.0.0.1:4343"
waf-cert-ca: "../KrakenWAF/certs/cert.pem"
```

The UI sends the token on both supported metrics paths:

```http
GET /metrics
Authorization: Bearer <token>
```

If `/metrics` is unavailable, the compatibility request to
`/__kwaf/metrics` carries the same header.

## Shared secret contract

Kraken UI deliberately uses the same secret name and file-first resolution
order as KrakenWAF:

1. `BEARER_PASSWORD_FILE`: path to a file containing the token.
2. `/run/secrets/krakenwaf/BEARER_PASSWORD`: conventional shared secret mount.
3. `BEARER_PASSWORD`: plain environment variable.

File contents and environment values are trimmed. Empty or unreadable files
fall through to the next source. Tokens must be non-empty ASCII strings, as
required for bearer credentials; Kraken UI refuses to start if a configured
token cannot be represented safely as an HTTP header.

The constructed `Authorization` header is marked sensitive in the HTTP client.
The token value is never included in application logs or dashboard errors.

## Local development

Set the same value before starting each process:

```bash
export BEARER_PASSWORD="$(openssl rand -hex 32)"

# Terminal 1
cd ../KrakenWAF
cargo run --bin krakenwaf

# Terminal 2, preserving the same BEARER_PASSWORD
cd ../kraken-ui
cargo run
```

For a short-lived local test, any non-empty ASCII value works. Generate a strong
random token for production.

## Shared file secret

When both services run on the same host, mount one credential where both can
read it:

```bash
sudo install -d -m 0750 /run/secrets/krakenwaf
openssl rand -hex 32 |
  sudo tee /run/secrets/krakenwaf/BEARER_PASSWORD >/dev/null
sudo chmod 0440 /run/secrets/krakenwaf/BEARER_PASSWORD
```

The file owner and group must allow both service accounts to read it. Neither
service needs an environment variable when the conventional path is used.

An explicit path can be selected for either service:

```bash
export BEARER_PASSWORD_FILE=/secure/path/krakenwaf-observability.token
```

## systemd

With systemd credentials, each service receives a private read-only copy of the
same root-owned source:

```ini
[Service]
LoadCredential=BEARER_PASSWORD:/etc/krakenwaf/secrets/BEARER_PASSWORD
Environment=BEARER_PASSWORD_FILE=%d/BEARER_PASSWORD
```

The ready-to-install Kraken UI drop-in is
[`../deploy/systemd/kraken-ui-bearer.conf`](../deploy/systemd/kraken-ui-bearer.conf).
Install it as:

```text
/etc/systemd/system/kraken-ui.service.d/bearer.conf
```

Then reload and restart the unit:

```bash
sudo systemctl daemon-reload
sudo systemctl restart kraken-ui
```

KrakenWAF's service must be provisioned with the same source token.

## Failure behaviour

| Result | Meaning | Action |
|---|---|---|
| HTTP `401` | Token missing or different from KrakenWAF's token. | Verify both processes resolve the same `BEARER_PASSWORD`. |
| HTTP `403` | Client IP is absent from KrakenWAF's observability allowlist. | Update `rules/addr/allowlist/allow_addrs_metrics_n_ui.txt`. |
| TLS error | `waf-cert-ca` does not trust the certificate served on port `4343`. | Configure the correct KrakenWAF certificate or CA PEM. |
| Connection refused | The dedicated observability listener is not running. | Start KrakenWAF and verify `metrics-port: 4343`. |

When no bearer secret is available, Kraken UI starts with a warning and sends
requests without `Authorization`. This supports KrakenWAF deployments where the
bearer gate is intentionally disabled, but authenticated production deployments
should always provision the token.

## Dashboard metrics

Bearer authentication changes transport authentication only. Kraken UI still
reads Prometheus text exposition from `/metrics`, including:

```text
krakenwaf_requests_inspected_total
krakenwaf_requests_blocked_total
krakenwaf_module_blocks_total{engine="cmc",module="overflow_detect"}
```

The dashboard renders `krakenwaf_module_blocks_total` labels as
`engine:module`. For example, a server response with
`engine="unknown",module="regex"` is displayed as `unknown:regex`; that label
originates in KrakenWAF's metrics output rather than being generated by the UI.
